# Coming soon: GenosDB 1.0 stable

GenosDB is completing its hardening phase. 1.0 will be the stable release, and this is what it will bring.

- **A definitive API.** The goal of 1.0 is an API that future improvements will add to and never alter, so that a second major version will never be needed. That is the result of architecture decisions taken early: a small surface — one boot call, a handful of verbs, one query language — with every capability an optional module behind it, and every format carrying its version. What evolves will live behind the surface; what you write against it will not change. From 1.0, Semantic Versioning will make it a rule: the public API, declared in `types/index.d.ts`, will not break within a major version; a deprecation will be announced in the [CHANGELOG](CHANGELOG.md) at least one minor release before removal, with its replacement; data stored by a build will be readable by every later build of the same major version.
- **Stable by default.** `latest` on npm will only ever receive stable releases. Experimental or breaking work will ship as pre-releases under the `next` tag (`npm i genosdb@next`), never in `latest`, and the public repository's `main` will carry stable builds only, so the CDN will never serve an experiment either.
- **Builds that last.** Already true today, and it will stay that way: every published build is complete in itself, with no runtime dependencies, no service behind it, no account, no key, nothing that expires and nothing that phones home. Once released, a build needs no maintenance to keep working. An application pinned to a version runs unchanged for as long as it is deployed, and its data lives on its users' devices in the format [CRYPTOGRAPHY.md](CRYPTOGRAPHY.md) specifies. Every build ever published stays on npm and on the CDN.
- **Full independence, if you want it.** Peer discovery is the one default that reaches outside the bundle: it reads the relay list published in this repository. Set `rtc.relayUrls` or run your own relay with the Fallback Server, and nothing in your deployment depends on anyone.
- **An engine that is specified.** The protocol in [CRYPTOGRAPHY.md](CRYPTOGRAPHY.md), every guarantee in [SECURITY.md](SECURITY.md) pinned by a conformance test, every release in the [CHANGELOG](CHANGELOG.md), independent reviews in [docs/audits](docs/audits/index.md). Maintenance builds on these documents, release after release.

1.0 will stabilize the API you build on today; the CHANGELOG and [MIGRATION.md](MIGRATION.md) record every step on the way. Try it, pin a version, and tell us in [Discussions](https://github.com/estebanrfp/gdb/discussions) what you build.
